4. Implementation of KRB5KRB_AP_ERR_SKEW handling
=======================================

4-1. Policy
=========

  a. Do not touch the Kerberos library and do the work on the kinkd side.

      Advantages
	- No need to ask the end user to replace libkrb5,
	  so it is easy to use.
      Disadvantages
	- It is necessary to touch private structures/functions.
	  -> Heavily dependent on the library version.

  b. Patch the library straightforwardly.

      Advantages
	- Probably straightforward to implement.
      Disadvantages
	- Users of kinkd must be told to replace libkrb5,
	  put a kinkd-specific one in another path, or
	  statically link it.
	- As before, dependent on the library version.

  c. Distribute the patched library together.
	Ehh...

	Actually, maybe this is the most reliable?
	What about the license?
	Which one to use? MIT, Heimdal, Shishi, ...

4-2. Current implementation
===============

	We are taking the direction of "a. Do not touch the Kerberos
	library; do the work on the kinkd side."

  4-2-1. Handling when ERR_SKEW occurs

	A function with a subset of the functionality of krb5_rd_req
	retrieves the keys etc. via krb5e_force_get_key and
	creates an auth_context.

  4-2-1. Adjusting the time when creating AP_REQ

    Heimdal
	krb5_context has members named kdc_sec_offset and
	kdc_usec_offset.
	Use these to shift the time only at the moment krb5_mk_req_extended() is called.

    MIT
	There are (private) functions krb5_get_time_offsets() and
	krb5_set_time_offset() that can set the time offset
	on a krb5_context.
	Use these to shift the time only at the moment krb5_mk_req_extended() is called.

4-3. Side notes
===========
	clarifications-06 3.1.5 describes time adjustment using the AS.

	MIT: done by default.
	Heimdal: [libdefaults] kdc_timesync option
	(whether it properly uses the nonce has not been confirmed)

	The time-adjustment implementation described in 4-2 abuses this feature.

5-2. Data structures
===============
	struct kink_global (@handle.h)
		Holds the global state of the KINK daemon (its own principal name,
		krb5_context, the TGT currently in use, epoch, etc.).
		Exactly one is created per process.

	struct kink_handle (@handle.h)
		One is created for each KINK transaction and holds its state.
		Exceptions:
		- When retrying right after the responder returns an error,
		  the kink_handle is reused even though it is a different transaction.
		  (when the ticket has expired, or on SKEW)
		- When parsing an ACK message, it is actually the same transaction,
		  but this is not known until it is parsed, so
		  a new kink_handle is allocated.

		All kink_handles are linked into a single queue for the scheduler
		(kink_global->schedq).

	struct ph2handle (@handle.h)
		Corresponds one-to-one with a kink_handle and holds the contents of the ISAKMP payload.
		It is a separate structure so that racoon1 code can be reused.

	struct kink_state (@handle.h)
		Indicates the state of a KINK transaction (waiting for GETSPI,
		waiting for REPLY, ...).
		A fixed number of states are prepared globally and
		pointed to from the kink_handle.

		State list
		 - Initiator states
			I_GETSPI	Waiting for the reply after issuing SADB_GETSPI.
			I_CREATE	Waiting for REPLY after sending CREATE.
			I_AGING		When ACK has been sent in the 3-way exchange,
					since the REPLY may be retransmitted,
					the state is retained.
			I_STALE		transaction complete.
					Waiting in preparation for SADB_EXPIRE.
			I_DELETE	Waiting for REPLY after sending DELETE.
			I_DELETE_HALF	After receiving REPLY, waiting on the grace
					timer until the inbound SA is removed.
			I_STATUS	Waiting for REPLY after sending STATUS.
		 - Responder states
			R_GETSPI	Waiting for the reply after issuing SADB_GETSPI.
			R_REPLY		After sending REPLY, waiting for ACK (when 3-way)
			R_AGING		After sending REPLY, a retransmission of the command
					may arrive, so the state is retained.
			R_STALE		transaction complete.
			R_DELETE_RECV	Immediately after receiving DELETE. It does not wait
					for anything in particular; it immediately
					transitions to R_DELETE_HALF. During rekeying,
					the old handle spawns a new handle for CREATE
					and one for DELETE, so this state is used when
					putting one of them (the one for DELETE)
					into the queue.
			R_DELETE_HALF	After sending REPLY, waiting on the grace
					timer until the inbound SA is removed.
			I_REKEYED	Used to delete the old handle
					later, during rekeying.
		 - Other states
			NONE		Immediately after a kink_handle is created.

	struct kink_addr (@handle.h)
		The addresses held by the local node.

		Addresses are checked periodically, and if any address has been
		created or deleted, the kink_addr list is updated accordingly.
		However, since kink_addr is referenced from struct kink_handle,
		the kink_addr may not be immediately removable even after the
		address disappears. Therefore, it is managed with a reference count (kink_addr->ref_cnt).

	struct kink_peer (@peer.h)
		Holds information about other KINK nodes (the service ticket
		for that node, epoch, etc.).
		It is identified using the principal name as the key.

		Every kink_peer is linked into either kink_global->peerlist or
		kink_global->deadpeerlist.

3.4. Flow of operation
=================

* Main loop @session.c
	Wait for events on the various sockets and on the next timeout
	computed by the scheduler
		PF_KEYv2 socket
		racoond socket (TCP)
		A socket prepared for each of the local node's addresses (UDP, bound)
		+ the timeout specification

	In the case of a timeout
		Control is returned to the scheduler, and
		the timeout handler is called from the scheduler.

		scheduler() @scheduler.c
		-> (*kink_handle->state->timeout)() @schduler.c
		   = timeout_i_getspi() @base.c
		or = timeout_r_create() @base.c
		...
		or = periodic_update_addrs() @session.c

	When an event occurs on the PF_KEYv2 socket
		handle_pfkey() @pfkey.c
		-> (*callback_acquire)() @pfkey.c
		   = callback_acquire() @session.c
		     -> acquire() @base.c
		          -> initiate1() @base.c
		-> (*callback_expire)() @pfkey.c
		   = callback_expire() @session.c
		     -> expire() @base.c
		          -> initiate1() @base.c
		-> (*job->callback)() @pfkey.c
		   = callback_i_getspi() @base.c
		or = callback_r_getspi() @base.c

	When an event occurs on the racoond socket
	(so far, only replies to FQDN QUERY)
		racoond_handler() @racoond_if.c
		-> racoond_read() @racoond_if.c
		     -> parse_rep_fqdn_query() @racoond_if.c
		          -> (*job->callback)() @racoond_if.c
		             = callback_i_racoond() @base.c

	When an event occurs on a network socket
		receive() @base.c
		-> handle_create() @base.c
		-> handle_reply() @base.c

* When SADB_ACQUIRE is received
	Main loop
	-> handle_pfkey() @pfkey.c
	    -> pk_recvacquire() @pfkey.c
	        -> (*callback_acquire)() @pfkey.c
	           = callback_acquire @session.c
	            -> acquire() @base.c
	                -> initiate1() @base.c
	                    Creation of the kink_handle.
	                    Take the necessary information out of SADB_ACQUIRE.
	                    (Currently, only the address is looked at.)
	                    To obtain the responder's principal name,
	                    send an FQDN QUERY to racoond and return for now.
	Main loop
	-> racoond_handler() @racoond_if.c
	    -> (*job->callback)() @racoond_if.c
	       = callback_i_racoond() @base.c
	        -> initiate2() @base.c
	            Proposal generation.
	            Send SADB_GETSPI to the kernel. Return for now.
	Main loop
	-> handle_pfkey() @pfkey.c
	    -> pk_recvgetspi() @pfkey.c
	        -> (*job->callback)() @pfkey.c
	           = callback_i_getspi() @base.c
	            -> initiate3() @base.c
	                ISAKMP payload generation.
	                KRB_AP_REQ generation.
	                    Obtain a Service Ticket if none exists.
	                    Obtain a TGT if none exists.
			KEYMAT computation
	                inbound SA creation.
	                Send the CREATE command. Return for now.
	Main loop
	-> receive() @base.c
	    -> read_udp_pacet() @base.c
	    -> handle_reply() @base.c
	        Look up the kink_handle from the received XID.
	        Decode the REPLY.

	        If the Kerberos part succeeded, an AP_REP should come back, so
		-> initate4() @base.c
	            epoch check.
	            Decode the ISAKMP payload.
	            Verify that the 1st proposal was accepted.
	            KEYMAT computation
	            outbound SA creation.
	            Key exchange complete. Return.
	If it is left alone without rekeying, it will eventually time out and
	-> scheduler() @scheduler.c
	    -> timeout_i_stale() @base.c
	        -> initiate6() @base.c
	            Release the krb authentication contexts.
	            The kink_handle disappears.

* When a CREATE message is received
	Main loop
	-> receive() @base.c
	    -> read_udp_packet() @base.c
	    -> handle_create( @base.c
	        -> respond_to_auth_command()
	            Decode the CREATE.
	            A KRB_AP_REQ should be attached, so extract it and check it.
	                The authentication context is created here.
	            Also decode the KINK_ENCRYPT.
	            From the cname attached to the ticket,
	            obtain the initiator's principal name.
	            epoch check.
	            -> respond1() @base.c
	                Decode the ISAKMP payload.
	                Check the proposal.
	                SADB_GETSPI. Return for now.
	Main loop
	-> handle_pfkey() @pfkey.c
	    -> pk_recvgetspi() @pfkey.c
	        -> (*job->callback)() @pfkey.c
	           = callback_r_getspi() @base.c
	            -> resopnd2() @base.c
	                ISAKMP payload generation.
	                KEYMAT computation.
	                inbound SA creation.
	                outbound SA creation.
	                Send the REPLY message.
	                Key exchange is tentatively complete. Return.
	Since the REPLY message may be lost and a CREATE may be retransmitted,
	wait for a while in the R_AGING state.

	(Note: for the responder, as soon as the key exchange completes;
	 for the initiator, once the time during which a retransmission
	 could arrive has passed (i.e., on entering I_STALE), the auth
	 context may be freed; the current implementation keeps it until the kink_handle is destroyed.)

3.5. Sockets
================
	PF_KEYv2 socket
		Held globally in the local variable fd_pfkey in session()@session.c
		and in kink_global->fd_pfkey.
	racoond socket
		A PF_UNSPEC/SOCK_STREAM socket to localhost.

		Held globally in the local variable fd_rcnd in session()@session.c
		and in kink_global->fd_rcnd.
	KINK socket
		Create one for each address the node has, and
		bind it to that address.
		A SOCK_DGRAM socket.
		For PF_INET6, set the IPV6_V6ONLY socket option.
		No per-socket policy is set for now.
		(-> Therefore, unless the SPD is configured so that the KINK port
		is not IPsec-protected, you will get stuck)

		Stored in struct kink_addr, and
		linked into the static variable addrlist in session.c.

	select() is used to wait for events on the sockets, but
	poll, kqueue, /dev/poll, or epoll should all work as well.
